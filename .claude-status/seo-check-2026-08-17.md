### 1. `/studio` is serving stale HTML — highest priority

The live page does not match the repo. Live `/studio` returns:

| | Live `/studio` | Every other page (`/`, `/projects`, `/projects/bose`, `/privacy-policy`) | Repo source |
|---|---|---|---|
| `<link rel="canonical">` | **absent** | present | `BaseLayout.astro:237` emits it for all non-noindex pages |
| Award badge / video paths | `/uploads/2026/06/best-ux-white.png` etc. | — | `studio.astro:399,402,417` use `/media/...` |
| `msapplication-TileImage` | `/uploads/2026/05/cropped-org-logo-270x270.png` | `/mstile-270x270.png` | `/mstile-270x270.png` |
| `viewport` | `width=device-width, initial-scale=1` | `...,viewport-fit=cover` | `...,viewport-fit=cover` |

`studio.astro` last changed **2026-08-02** (`b454d39`) and already used `/media/` paths then; the canonical logic landed **2026-08-09** (`22f82db`). The served HTML predates both, so this looks like an edge/CDN cache pinned to a pre-August deploy, not a source bug.

**Why it matters:** `/studio` is the 301 destination for `/about/` *and* `/services/`. Google following those redirects lands on a page with **no canonical tag**, and its images are resolving through a second `/uploads/ → /media/` 301 hop.

**To do:** force a redeploy / purge the Vercel cache for `/studio`, then re-fetch and confirm the canonical tag and `/media/` paths appear. If it persists after a clean redeploy, the problem is in the build, not the cache.
